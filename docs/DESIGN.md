## 1. 目标与非目标

### 目标
- 把任意高清位图转换为**受控的低分辨率像素图**：尺寸、颜色数、调色板、抖动方式全部可调、可复现。
- 转换结果**可手工逐像素修改**，且修改成果不因调整转换参数而丢失。
- 输出能直接用作美术素材：PNG（1x/放大）、精灵图集、调色板文件、GIF、以及 Minecraft 建造蓝图。
- 单人本地使用：零部署、零网络、双击可用。

### 非目标
- ❌ 不是通用图像编辑器（不做图层混合模式、滤镜库、笔刷引擎、矢量工具）
- ❌ 不做图转 3D 模型 / 体素化 / .schematic 二进制写入（蓝图做到「可照搭的图纸」为止）
- ❌ 不做云端存储、协作、账号体系
- ❌ 不追求「一键出神图」，自动算法定位是**出草稿**，成品靠手调

## 2. 技术选型

| 关注点 | 选择 | 理由 / 被否决的方案 |
| --- | --- | --- |
| 形态 | 本地 Web 应用（Vite dev server / 静态打包） | 图像处理天然适合浏览器；否决 Electron（体积）、PySide6（UI 开发慢）、单文件 HTML（难维护） |
| 语言 | TypeScript（`strict: true`） | 像素级索引与缓冲区操作极易越界，类型能挡住一大类错误 |
| 构建 | Vite | 零配置、HMR 快、`build` 产出纯静态文件可离线用 |
| UI | React 19 | 面板数量多（转换/调色板/导出/批量/状态栏），组件化收益明确 |
| 状态 | Zustand | 轻量；关键是**能脱离 React 在工具函数里 `getState()`**，这对画布事件处理很重要 |
| 绘图 | Canvas 2D | `getImageData/putImageData` 直接拿到逐像素缓冲；放大用 `imageSmoothingEnabled = false` 即得硬边像素 |
| 重计算 | Web Worker + OffscreenCanvas | 转换流水线是 O(w·h) 的循环，放主线程会卡；用 transferable 传 `ArrayBuffer` 零拷贝 |
| 撤销 | 自研命令栈（带快照） | 像素网格操作是「整块数据替换」模型，通用 undo 库反而绕 |
| 依赖 | 运行时依赖仅 `react` `react-dom` `zustand`；`fflate`、`gifenc` 在对应导出功能实现时按需引入 | 保持依赖面小，避免供应链与体积膨胀 |

**为什么不用 WebGL 做转换**：降采样 + 量化本质是每像素独立或小邻域运算，CPU 循环配合 `Uint8Array` 已经足够快（1024×1024 → 32×32 的量化是毫秒级）；且抖动的误差扩散是**串行依赖**的，GPU 并不擅长。WebGL 只在需要实时预览超大图时才考虑，目前不必要。

## 3. 核心数据模型

全部定义在 `src/core/types.ts`。

### 3.1 调色板

```ts
type RGBA = readonly [r: number, g: number, b: number, a: number]; // 0-255

interface Palette {
  id: string;
  name: string;
  colors: RGBA[];        // 上限 256（索引存 Uint8Array）
  builtin?: boolean;
  source?: 'builtin' | 'extracted' | 'imported';
}
```

约束：**索引存进 `Uint8Array`，所以调色板上限 256 色**。这个上限对像素艺术绰绰有余（PICO-8 只有 16），也省掉一个字节的大小分支。

### 3.2 像素网格（核心工作对象）

```ts
interface PixelGrid {
  w: number;
  h: number;
  indices: Uint8Array;   // 长度 w*h，值为调色板索引
  alpha: Uint8Array;     // 长度 w*h，0-255，独立于调色板
}
```

**为什么 alpha 独立、不用一个「透明色」哨兵值**：
- 素材常需要半透明边缘（发光、阴影、渐变），单哨兵值表达不了；
- 导出 PNG 时 alpha 直接写回，不需要在调色板里塞一个魔法槽位；
- 全局换色（把 A 色换成 B 色）不会误伤透明区。

### 3.3 转换参数

```ts
interface ConvertSettings {
  targetW: number;             // 目标格数（宽）
  targetH: number | 'auto';    // 'auto' = 按原图宽高比推导
  sampling: 'nearest' | 'area' | 'dominant' | 'median';

  quantize: 'palette' | 'kmeans';
  paletteId: string;           // quantize === 'palette' 时生效
  maxColors: number;           // quantize === 'kmeans' 时生效，2-256
  distance: 'rgb' | 'weighted' | 'lab';

  dither: 'none' | 'bayer2' | 'bayer4' | 'bayer8'
        | 'floyd' | 'atkinson' | 'sierra';
  ditherStrength: number;      // 0-1

  preprocess: {
    brightness: number;        // -100 ~ 100
    contrast: number;          // -100 ~ 100
    saturation: number;        // -100 ~ 100
    sharpen: number;           // 0 ~ 100
    alphaThreshold: number;    // 0-255，低于此值视为全透明；255 表示不处理
  };

  trimTransparent: boolean;    // 转换后裁掉四周全透明边
  pixelPerfect: boolean;       // 禁止产生「半格」，见 §4.2
}
```

`ConvertSettings` 是**纯数据、可 JSON 序列化**的 —— 这直接支撑了预置保存、项目存档、批量复用三个功能。

### 3.4 双层编辑模型（关键设计）

```ts
interface EditLayer {
  /** 与 baseGrid 同尺寸；null 表示该格走底层，有值表示被手工覆盖 */
  cells: (PixelCell | null)[];
}
interface PixelCell { index: number; alpha: number; }

interface Document {
  source: SourceImage;
  settings: ConvertSettings;
  baseGrid: PixelGrid;         // 由 settings 重算得出（可重入）
  editLayer: EditLayer;        // 用户手工改动（不可重算）
  palette: Palette;
}
```

**渲染时合成**：`composite(i, j) = editLayer.cells[k] ?? baseGrid[k]`。

**这个设计换来什么**：

| 场景 | 没有双层模型 | 有双层模型 |
| --- | --- | --- |
| 转完 32×32 后手改了半天，又想试试 48×48 | 手改全丢，重画 | 改回 32×32 手改立刻回来；切 48×48 时编辑层按比例缩放重采样 |
| 想换调色板看效果 | 手改的像素被一起改掉，或者不变但和背景不搭 | 手改的格子**不受重算影响**：它们的索引是你明确选的，底色随调色板变 |
| 想改抖动强度 | 手改被冲掉 | 只影响底层，手改不动 |

**一处要说清楚的边界**：`PixelCell` 存的是**调色板索引**而非颜色值。所以
「换调色板时手改的像素保持原来的颜色」只在同一个调色板内成立；整体换到另一套调色板
（M3）时，手改格子的索引会指向新调色板里的对应槽位，颜色随之改变 —— 这是索引式存储的
必然结果，也是全局换色能一路改到手改区域的原因（见 §6）。

**代价与取舍**：切换尺寸时编辑层必须做一次「最近邻重采样」，非整数倍时手改像素位置会有半格以内的偏移 —— 这是可接受的，重采样后会弹提示告知影响了几格（不是弹窗确认：拖动尺寸滑块会连续触发，弹窗会成为噪音）。另一处代价是合成多一次查表，但 32×32 只有 1024 格，可忽略。

**另一条被否决的路**：把手工操作记成操作日志（operation log）重放。否决原因：全局换色、自动描边这类操作依赖当前全图状态，重放语义不清晰；且日志体积随时间增长。快照式编辑层简单可靠。

## 4. 转换流水线

`src/core/pipeline.ts`，在 Web Worker 中执行。

```
源 ImageData
  ↓ ① 预处理        preprocess.ts
  ↓ ② 降采样        sampling.ts      → (targetW × targetH) 的 RGBA 缓冲
  ↓ ③ 颜色量化      quantize.ts      → indices + alpha
  ↓ ④ （抖动）       dither.ts        与 ③ 交织执行
  ↓ ⑤ 后处理        trim / 透明清理
PixelGrid
```

### 4.1 降采样 `sampling`

| 模式 | 做法 | 适用 |
| --- | --- | --- |
| `nearest` | 取块中心像素 | 保留原始硬边缘；原图本身就是像素画时用 |
| `area` | 取块内所有像素的加权平均 | **默认**。照片/插画降采样最稳，颜色过渡自然 |
| `dominant` | 块内颜色做直方图（量化到 5bit/通道后投票），取占比最高 | 想要「色块感」、避免产生原图不存在的混合色 |
| `median` | 块内各通道取中位数 | 抗噪点、抗单点高光污染 |

实现要点：
- `area` 的块边界要处理**非整数倍缩放**带来的部分覆盖，用累积权重而不是简单丢像素，否则会出现规则条纹。
- 全程在 `Uint8ClampedArray` 上循环，行内累加避免重复查表。

### 4.2 pixelPerfect

当目标格数与原图尺寸不是整数倍关系时，`area` 平均会让某些格子覆盖 2 个源像素、某些覆盖 3 个，导致**同一视觉元素在不同位置大小不一**（像素画的经典瑕疵）。

`pixelPerfect: true` 时：先把原图用最近邻缩放到「目标格数 × 整数倍」的中间尺寸，再做整数倍面积平均，保证每格权重完全一致。代价是牺牲一点锐度，换来网格规整。

### 4.3 颜色量化 `quantize`

**模式 A：映射到固定调色板**

对每个像素，在调色板中找最近色。距离度量三选一：

| 度量 | 公式要点 | 特点 |
| --- | --- | --- |
| `rgb` | 欧氏距离 | 最快，但对暗部/肤色判断偏差大 |
| `weighted` | `2·Δr² + 4·Δg² + 3·Δb²` | 便宜的感知近似，实时预览默认 |
| `lab` | 转到 CIELAB 空间算 ΔE76 | 最准，代价是每像素一次色彩空间转换 |

优化：`lab` 模式下**预先把调色板转到 LAB 一次**（只转 ≤256 个），源像素转换在线做。另外做一个 32×32×32 的 5bit/通道查找缓存表（`Uint8Array(32768)`）——同一张图在预览滑动时大量颜色重复，命中率很高。

**模式 B：k-means 限制色彩数**

1. 用「最大最小距离法（k-means++ 的简化版）」从图像中采样初始聚类中心，避免随机初始化导致每次结果不同；
2. 迭代 8–12 次（像素艺术不需要收敛到极致）；
3. 簇中心即为新调色板，写回 `Palette`，同时把图像映射上去。

**抖动与量化交织**：误差扩散类抖动必须在量化过程中进行 —— 量化当前像素 → 计算误差 → 扩散到尚未处理的邻居。因此 `quantize` 与 `dither` 在实现上是同一个循环的两面，接口设计为：

```ts
function quantizeInto(
  src: Uint8ClampedArray, w: number, h: number,
  palette: RGBA[], opts: QuantizeOptions,
  out: { indices: Uint8Array; alpha: Uint8Array },
): void;
```
`opts.dither !== 'none'` 时内部走误差扩散路径，否则走纯最近色映射路径。

| 抖动 | 特征 |
| --- | --- |
| `bayer2/4/8` | 有序抖动，图案规则、可无缝平铺，强度用阈值矩阵幅值控制 |
| `floyd` | 经典误差扩散，细节最好，但有「虫形」伪影 |
| `atkinson` | 只扩散 3/4 的误差，对比度高、干净，**像素画首选** |
| `sierra` | 介于 floyd 与 atkinson 之间 |

`ditherStrength` 统一缩放到扩散量（`err * strength`），有序抖动则缩放阈值矩阵幅值。

## 5. 编辑器设计

### 5.1 工具集

`src/core/tools/`，每个工具实现统一接口（M2 已落地）：

```ts
interface Tool {
  id: ToolId;
  label: string;
  key: string;            // 快捷键
  kind: 'paint' | 'shape' | 'pick' | 'select';   // 调用方据此驱动
  hint: string;
  down?(ctx, changes, p): void;              // 落笔即时生效（铅笔/橡皮/油漆桶）
  drag?(ctx, changes, from, to): void;       // 拖拽中增量生效（自由绘制）
  commit?(ctx, changes, from, to): void;     // 抬起时一次性生效（形状/选区搬运）
  preview?(ctx, from, to): GridPoint[];      // 拖拽预览要标记的格子
}
```

三条实现约定，比接口本身更重要：

1. **工具不持有状态**。一次拖拽的起点/终点由调用方（`state/paint.ts`）保管，
   工具是纯函数式的回调集合，因此可以直接单测、也能被反复复用。
2. **工具不碰画布**。预览以「格坐标列表」返回，覆盖层决定怎么画 ——
   这样 `tools/` 与 `core/` 一样保持零 DOM 依赖，测试能直接在 node 里跑。
3. **预览与落笔共用同一份光栅化结果**（`shapePoints`），所以「拖拽时看到的形状」
   与「松手后画出来的形状」不可能不一致。

`changes` 是 `Map<格下标, 改动前的值>`：写入前先记账，这是撤销栈的数据来源，
同一格在一次操作里只记第一次。

| 工具 | 说明 |
| --- | --- |
| 铅笔 `B` | 画前景色；笔刷尺寸 1–4（以落点为中心）；开启对称时同时写入镜像位置；拖拽用 Bresenham 补点，快速拖动不断线 |
| 橡皮 `E` | 写入 `{index:0, alpha:0}` 而不是「删掉覆盖项」—— 后者会让底层颜色重新露出来 |
| 油漆桶 `G` | 4 邻域洪水填充，按「合成后的索引 + alpha 完全相同」判定连通；结果同样走对称展开 |
| 吸管 `I` | 取该格当前生效的索引为前景色；`Alt` 临时切换。**它不实现为工具回调**：取色要写回 store 的前景色，给它开一条「写回值」的通道会让接口变复杂，而它本来就不改网格 |
| 直线 `L` / 矩形 `R` / 椭圆 `O` | 拖拽起点终点；矩形/椭圆可选描边或填充。椭圆用「掩码 + 取边界」而非中点算法：小尺寸下中点算法会给出一条断开且不对称的细线 |
| 选区移动 `M` | 拖空白处框选；在选区内拖拽搬运（剪切-粘贴）。搬运 = 先快照源区合成值 → 源区置透明 → 目标区写入快照，顺序不能反，否则源与目标重叠时会读到刚写进去的值 |

### 5.2 撤销栈

`src/state/history.ts`，命令栈 + 快照：

- 一次「操作」= 一次 `onDown → onUp`（拖拽过程中的中间态不单独入栈），避免拖一笔产生几百条记录。
- 快照只存**被修改的格子**（`k → PixelCell` 的稀疏 Map），不存整张网格。32×32 全图也就 1KB，稀疏化是为了将来支持大尺寸。
- 容量 100 步，环形覆盖；超过后丢最旧的。
- 与撤销栈解耦：**转换参数变更不入撤销栈**，它改的是 `baseGrid`，属于另一个维度的历史（由「最近一次转换设置」表达）。

落地时的两个补充：

- 一条记录存 **before 与 after 两侧**（`{index, before, after}`），因为重做需要知道「改成什么」，
  而共享一份快照需要额外约定方向，不如直接存两侧清楚。
- 结算时**丢掉改回原值的格子**（画了又擦回去）。否则栈里会堆一批「撤销一次什么都看不出来」的空操作。
  注意判据是编辑层的值，不是视觉值：用与底层相同的颜色落笔仍会记下这一格 —— 它是显式的覆盖，
  可撤销、语义一致，比「静默地什么都不做」好推理。

### 5.3 画布交互 `Viewport.tsx` + `canvasDraw.ts`

- **两层 canvas**：底层绘制像素（只在网格数据变化时重绘），上层绘制网格线、选区、笔刷光标、预览图形（跟随鼠标频繁重绘）。分离后鼠标移动不会触发整图重绘。
- 缩放：0.02x–64x，`imageSmoothingEnabled = false` + 离屏小画布（尺寸 = 网格尺寸），避免每帧 `putImageData` 到全尺寸画布。
- 平移：空格拖拽 / 中键拖拽；`+` `-` 缩放；`0` 适配窗口；`1` 原尺寸。
- 坐标反查：`gridX = floor((mouseX - panX) / (previewW × zoom / gridW))`。
- 网格线：有转换结果时画**格网**（编辑时的参考系），没有结果时画源像素网格。
  格边长 < 4px 时不画；网格超过 128 格时每 4 格一条（防摩尔纹），每 8 条强调一次。
- 棋盘格底用 **CanvasPattern** 而不是逐格 `fillRect`：铺满一屏需要上万次 fillRect，
  而鼠标每动一下都要重绘一次。
- 落笔范围：`result` 视图整张可画；`split` 视图只在分割线右侧可画（左侧是原图，
  在那里落笔画的是看不见的地方）；`sideBySide` / `source` 不响应绘制并在画布上给出提示。

### 5.5 智能辅助（M4）

`src/core/assists/`。三个功能，共同点是**不追求「一键出神图」**：
自动算法只负责把最费手的重复劳动做掉，最后的细节仍旧手调。

| 模块 | 做什么 | 关键取舍 |
| --- | --- | --- |
| `outline.ts` | 给非透明区域勾一圈轮廓 | 4/8 邻域与外缘/内缘/两侧可选；写值前先跳过「本来就已经是轮廓色」的格子，否则连点两次会看到「改了 N 格」却什么都没变，撤销栈里还会多一条空操作 |
| `shade.ts` | 按亮度把画面压成阴影/中间调/高光三层 | **档位只用来定「目标亮度」（区间中点），候选色在整块调色板里找最近的**。这里走过一次弯路：按格自身亮度归类再在**同档**里找最近色，若包含原色则最近的永远是它自己（模块空操作），排除原色则等于换成同亮度、别的色相的兄弟色（中灰变中红）—— 那比空操作更糟。正确做法是把颜色**缩放到目标亮度**再就近映射：压暗按比例乘、提亮朝白 lerp，色相得以保留。纯黑/纯白跳过（缩放会除零，且它们本来就没有色相可言） |
| `tile.ts` | 检查平铺接缝 | 判据是「索引 + alpha 完全相同」，与洪水填充口径一致：颜色一样但一边更透，在贴图软件里同样看得出缝 |

**接线方式**：三个模块都返回 `CellWrite[]`（下标 + 目标值），由 store 一次性
`applyEditWrites` 落进编辑层并记成一条撤销记录。所以每个辅助操作都**能 Ctrl+Z 撤销**，
也都不会被转换参数重算冲掉 —— 这与画笔走的是同一条记账路径。

**边缘色晕清理**（`preprocess.applyDecontaminate`）放在 `preprocess.ts` 里，
因为它是降采样前的源图处理。顺序不能反：它要靠「谁还是半透明」来判断边缘，
所以必须在 α 阈值之后执行。它只改 RGB 不动 alpha —— 边缘的柔和过渡该保留还保留，
只是它通往的颜色换成了主体色。

## 6. 调色板引擎

`src/palettes/`

- **`builtin.ts`**：内置调色板数据 + `resolvePalette(id, customs)`。核心是 Minecraft 16 染料色：

  ```
  white #F9FFFE   light_gray #9D9D97   gray #474F52    black #1D1D21
  brown #835432   red #B02E26          orange #F9801D  yellow #FED83D
  lime #80C71F    green #5E7C16        cyan #169C9C    light_blue #3AB3DA
  blue #3C44AA    purple #8932B8       magenta #C74EBD pink #F38BAA
  ```

  另附：MC 混凝土 16（与染料板槽位一一对应）、PICO-8（16）、GameBoy（4 阶灰绿）、
  NES 子集 24、C64（16，Pepto 校准值）、DawnBringer 16、灰阶 8 级、黑白 2 色。

  **内置板是只读的常量**。任何改色操作都会先分叉出一块自定义板 —— 就地修改共享对象
  会让所有用同一块板的地方一起变色，而且刷新后又恢复原样，属于最难排查的一类 bug。

- **`parse.ts`**：解析与序列化 `.hex`（每行一个色值，最常见的交换格式）、
  `.gpl`（GIMP Palette）、`.pal`（JASC-PAL）。解析失败一律返回 `null` 不抛异常。
  有一个容易踩的坑：`.hex` 的注释行与 `#RRGGBB` 都以 `#` 开头，
  不能按首字符过滤，正确做法是剥掉 `#` 后看剩下的是否恰好是 3/6 位十六进制。

- **`extract.ts`**：从图片提取主色。默认走「中位切分（median cut）」——比 k-means 快且
  无需迭代，取色结果更「散得开」，更适合做调色板；同时提供 `kmeans` 备选。
  两个过滤器解决「提出来一堆背景色」这个最常见的抱怨：排除透明像素、限定明度区间。
  提色结果**不自动套用**，先给预览让用户决定存不存。

- **`ops.ts`**：排序（明度 / 色相）、合并近似色，以及**索引重映射**。
  这里的危险点在于：调色板一被重排，`PixelGrid.indices` 与编辑层的 `PixelCell.index`
  就全部指错槽位。所以每个操作都返回 `map[旧索引] = 新索引`，
  调用方必须把底图与编辑层**一起**重映射 —— 漏掉编辑层的话画面看着正常，
  手改的格子却会突然变色。

- **全局换色（palette replace）**：`Shift + 点击色块` → 把全图中该色换成前景色。
  实现上**写进编辑层**而不是改底图：底图由参数重算得出，改它下次调参就白改了；
  写进编辑层则天然持久、天然可撤销（走与画笔同一条记账路径）。
  代价是「手改格数」会跳一截，这是诚实的 —— 那些格子确实被改过了。

- **k-means 限色模式**（`core/color/kmeans.ts`）：从**降采样后**的图上聚出 N 个代表色
  当调色板。原图 400 万像素聚类要几百毫秒，而目标格数最多 6.5 万格，
  其颜色分布已经足够代表最终这张像素图 —— 我们要的是「这张像素图该用哪些色」，
  不是「原图有哪些色」。初始化用最大最小距离法而非随机采样，保证**结果确定**：
  同一张图跑两次必须给出同一块板，否则每拖一次滑块手改的颜色就乱跳。
  生成的板随结果回传（`ConvertResult.generatedPalette`），理由与决策 13 相同。

## 7. 导出体系

`src/core/exporters/`，统一接口：

```ts
interface Exporter {
  id: string;
  label: string;
  options: OptionSchema[];     // 供 UI 自动渲染参数控件
  run(doc: Document, opts: Record<string, unknown>): Promise<Blob | Blob[]>;
}
```

| 导出器 | 说明 |
| --- | --- |
| `png.ts` | 1x 或 Nx 放大。放大必须用**整数倍最近邻**手写循环，不能依赖 `drawImage` 的平滑（不同浏览器插值行为不一致） |
| `spritesheet.ts` | 多图/多帧按行打包，列数默认接近正方形；可选裁剪透明边（`trim`）；可选间距；附坐标 JSON。输入取自批量队列的已完成项 |
| `gridJson.ts` | `{w, h, palette: string[], indices: number[], alpha?: number[]}`，给程序消费。全不透明时省略 alpha，有一格半透明就必须写 |
| `blueprint.ts` | Minecraft 建造蓝图：网格 + 每行/列坐标标尺 + 本页色号图例 + 分页 + `x,y,z,block` CSV + 色号↔方块对照表 |
| `palette`（在 `PaletteIoPanel` 内） | `.hex` / `.gpl` / 色条 PNG（每色一格，带细黑边框） |
| `gif.ts` | 逐帧跑同一套 `ConvertSettings`，再用 `gifenc` 编码；注意 GIF 只有 256 色且单色透明，需提示用户。**M6 未做**，理由见 ROADMAP |

`registry.ts` 把所有导出器登记成**自带选项 schema** 的对象，`ExportPanel.tsx` 照着 schema 渲染控件：

```ts
interface Exporter {
  id: string;
  label: string;
  description: string;
  needs: 'grid' | 'batch';       // 需要哪类输入，面板据此决定按钮可不可点
  options: ExportOption[];       // number / toggle / select 三种，含默认值与范围
  run(ctx: ExportContext, values: ExportOptionValues): Promise<ExportResult>;
}
```

这样加一个导出器只要写一个对象，不用再改面板；选项的范围、默认值、提示文案只有一处定义，
不会出现「面板限制 1–64 而导出器按 1–32 处理」这种对不上的情况。
`mergeOptionValues` 按 **schema 的 key** 逐个取值而不是展开合并 —— 选项被删改过之后，
旧字段不会一路留在状态里再被写回存储。

**蓝图色 → 方块映射（M6 落地版）**：**按颜色的 hex 键**存用户覆盖，没配过的用「离该颜色最近的方块」现算。

- 为什么不按槽位序号：槽位顺序会被排序 / 合并近似色改变（见决策 26 的索引重映射），
  按序号存的映射会在用户整理调色板之后整体错位，而且错得毫无提示。
- 为什么默认值是算出来的：Minecraft 没有精确等于某个 hex 的方块，颜色匹配天然是
  「最接近」而非「相等」。给 60 多个候选方块各标一个代表色，按加权 RGB 找最近，
  任意调色板（包括自定义板）都能得到一份说得过去的初值；硬编码只能覆盖内置板。
- 选羊毛 / 混凝土两块板时，因为色值与方块表逐条对应，默认映射会**精确命中**。
- 映射表持久化在 localStorage：那是用户一个个挑出来的结果，刷新就没了的话没人愿意配第二遍。

### 7.1 批量打包（M5）

批量导出不走上面的 `Exporter` 注册表 —— 它是「N 张图 + 一份报告」的整体产出，
不是单个文档的导出参数。实现在两处：

- `core/batch/naming.ts`：命名模板与去重（纯字符串，可单测）
- `core/batch/zip.ts`：ZIP 打包（store 模式）
- `state/batch.ts`：`buildBatchZip()` 逐张编码 PNG + 附调色板与 `report.txt`

| 包内内容 | 说明 |
| --- | --- |
| `<模板>.png` × N | 1x 或整数倍放大；名字由模板生成并去重 |
| `palette.hex` | 用到的调色板。k-means 限色下每张图的板可能不同，那就一块板一个文件（`palette-1.hex`…） |
| `report.txt` | 逐张的导出名 / 源文件 / 网格 / 输出像素 / 用色 / 耗时，末尾附命名模板 |

**为什么不用 `fflate`**（原计划）：包里的输入全是 PNG，而 PNG 内部已经是 DEFLATE 压缩数据，
对已压缩数据再压一遍通常只有不到 1% 的收益，却要付出一次全量 CPU 遍历外加一个 30KB 起步的依赖。
store 模式的 ZIP 结构（本地头 + 中央目录 + 尾部记录）一百多行能写对，而且能被单测直接回读校验。
代价明确写在这里：只支持单卷、单条目 < 4GB、不支持 zip64 与加密 —— 对「一次几十张 PNG」足够。

### 7.2 存档与持久化（M7）

两套机制，各管一段，不要混用：

| 机制 | 存什么 | 存在哪 | 什么时候写 |
| --- | --- | --- | --- |
| `.pixproj` 存档 | **一份工作**：源图 + 参数 + 调色板 + baseGrid + 编辑层 | 用户下载的文件 | 显式点「存档」 |
| localStorage | **长期偏好**：自定义调色板、批处理预设、转换预设、导出选项、方块映射 | 浏览器本地 | 每次改动即写 |

为什么不做「自动保存当前工作到 localStorage」：刷新页面后悄悄回来一张图，
用户会以为自己没关掉它 —— 而如果是别人的电脑，那就是意外泄露。显式存档更符合直觉。

`.pixproj` 的结构（JSON）：

```ts
{
  version: 2, savedAt, name,
  source: string,              // 内嵌源图：导入时的原始字节，data URL
  originalWidth, originalHeight,
  settings: ConvertSettings,
  palette: Palette,
  baseGrid: { w, h, indices: number[], alpha: number[] } | null,
  edit:     { w, h, rows: number[], index: number[], alpha: number[] } | null
}
```

**源图内嵌而不存引用**：浏览器不允许序列化本地文件路径，File System Access API 又要重新授权。
存引用的话，第二天打开存档第一件事是「请重新选择原图」—— 那这个存档基本等于没用。
所以存**导入时的原始字节**（JPEG 原样存，不重新编码成 PNG：对照片能小 3–5 倍）。

**编辑层用 CSR 三数组稀疏存**：512×512 的编辑层直接 JSON 要 26 万个 `null` 字面量，
而手改通常只有几百格，稀疏存能小三个数量级。

**校验从严**：`edit` / `baseGrid` / `palette` 各自独立校验，任一段坏掉只丢那一段并明确提示。
但**读取时先清空再写入**是关键顺序 —— `loadSource` 内部会 `clearResult`（换图必须作废旧结果），
编辑层写在它之前就会被一起清掉，而且表现是「画面只是少了手改」，不报错不提示。

## 8. 性能策略

| 场景 | 手段 |
| --- | --- |
| 转换流水线 | 放 Web Worker；`ArrayBuffer` 通过 `transferable` 传递（零拷贝） |
| 参数拖动时的高频重算 | 拖拽中降级：`distance` 强制为 `weighted`、跳过 `lab`；`pointerup` 后再跑完整精度 |
| 预览渲染 | 网格数据 → `ImageBitmap` 预渲染一次，缩放只做 `drawImage` |
| 大图源数据 | 超过 4096px 的源图先做一次 downscale 缓存（保留一份「适合当前 targetW 的源副本」，最多到 targetW 的 32 倍） |
| 查找表 | LAB 最近色用 5bit/通道 的 32K 缓存表 |
| 长列表（批量队列） | 列表限高 + 滚动，不做虚拟滚动：队列是用户自己一张张拖进来的，几十项以内，虚拟滚动反而让「展开某项改参数」变复杂 |
| 批量转换 | 串行跑在**第二个** Worker 实例上：不与编辑器的预览请求抢同一条在途请求，同时批量也不需要「只保留最新一次」的合并策略 |
| 批量解码 | 走 `decodeImage()`（只要像素数据）而不是 `loadSourceImage()`：后者会额外留一份最长边 2048 的显示位图，20 张图就是几百 MB |

## 10. 测试

`core/` 与 `palettes/` 不依赖 DOM，所以能直接在 Node 里跑单元测试（vitest，`environment: 'node'`）。
这本身就是对「逻辑与 UI 分离」这条架构规则的持续验证 —— 哪天有人在 `core/` 里
误引入 DOM 依赖，测试会立刻跑不起来。

渲染与导出层用到了 `ImageData`，Node 里没有这个全局对象。为了不为此拉进整个 jsdom，
测试环境里放了一个最小实现（`src/core/__testing__/setup.ts`），
这样「网格 → 像素缓冲 → 整数倍放大」这条导出路径也能被覆盖。

测试重点放在**容易静默出错**的地方，而不是追求覆盖率数字：

| 测什么 | 为什么 |
| --- | --- |
| alpha 预乘（降采样） | 不预乘也能出一个「看起来还行」的结果，只是边缘有脏色，很难发现 |
| 透明像素不参与误差扩散 | 扩散进去会把透明区的 alpha 改写，边缘出现噪点 |
| 切换调色板不越界 | 曾经的崩溃点（缓存跨调色板复用），见决策 12 |
| 直方图投票不漏桶 | 曾经 `touched` 容量不足，大格子里静默偏向先扫到的颜色 |
| 抖动强度 0 ≡ 不抖动 | 六种抖动模式逐一对比，确保没有漏掉某个模式的分支 |
| 整数倍放大不产生插值色 | 导出硬边是验收标准；用「输出颜色集合 ⊆ 输入颜色集合」来断言 |
| 相同输入两次结果一致 | 抖动是串行依赖的，任何隐藏状态都会破坏确定性 |
| 手改不被重算冲掉（M2 核心验收） | 这是整个工具对用户的核心承诺，破了就没人敢调参数了 |
| 尺寸连续变化不累积失真 | 「从基准层重采样」这条设计如果写错，表现是「拖动尺寸滑块手改逐渐消失」，很难察觉 |
| 对称镜像的去重与越界裁剪 | 笔刷压在中轴上会写出重复格，贴近画布边缘会画到图像外 |
| 图形光栅化对称、预览 = 落笔 | 预览与落笔共用同一份结果，测试直接断言两者格子数相等 |
| 选区搬运在源/目标重叠时正确 | 先快照再写，顺序写反会静默吃值 |
| 洪水填充按索引 + alpha 判定 | 只用索引会在半透明边缘处越界填充 |
| 撤销栈的环形容量与重做分支截断 | 超过 100 步后「撤销 → 新操作 → 重做」的组合最容易出错 |
| 编辑层就地修改的可见性 | 就地改不换引用，靠 `editVersion` 通知；这条链断了就是「画了但看不见」 |
| 排序/合并后画面不变 | 索引与调色板必须同步重映射；只改调色板会让手改像素静默变色 |
| 内置调色板数据完整性（M3） | id 唯一、色值合法、板内无重复色 —— 重复色不会报错，只会让统计虚高、抖动浪费槽位 |
| 提色能还原纯色块 | 四个纯色块应该提回四个色；提不出来说明中位切分的切分/平均写错了 |
| k-means 的确定性 | 同一输入两次必须完全一致，否则调参时颜色会乱跳 |
| `.hex` 的 `#` 二义性 | `#F9FFFE` 是颜色、`# 注释` 是注释 —— 按首字符过滤就会把颜色行整片吃掉 |
| 换色 / 撤销 / 编辑层三者同步 | 换色只改底图的话，下次调参就白改；撤销不回滚编辑层的话，手改像素会变色 |
| 描边不重复产生空操作（M4） | 连点两次描边不该出现「改了 N 格」却毫无变化，撤销栈也不该多一条空记录 |
| 明暗分层要真的改变亮度、且守住色相（M4） | 这里踩过一次坑：同档内取最近色会退化成空操作或乱换色相；用例断言「中亮度的绿应落到绿而不是同亮度的灰」 |
| 去背顺序（α 阈值 → 色晕清理） | 顺序反了会把背景色一起搬进边缘；只开阈值则会留一圈灰边 |
| 色晕清理不动 alpha | 边缘的柔和过渡该保留还保留，只换它通往的颜色 |
| 接缝检查把半透明差异也算缝 | 只比索引会漏掉「颜色一样但一边更透」这种可看出的缝 |
| 平铺预览的取整 | 不取整时渲染自己会制造 1px 接缝，正好污染了它要检查的东西 |
| 命名去重忽略大小写（M5） | Windows / macOS 默认不区分大小写，`A.png` 与 `a.png` 在 zip 里是两个条目，解压时却互相覆盖 |
| 序号插在扩展名前 | `a.png` 去重写成 `a.png_2` 的话，导出目录里就是一堆没有扩展名的文件 |
| 未知占位符原样保留 | 静默替换成空串会产出 `_.png` 这种名字，用户看不出是自己模板写错了 |
| ZIP 结构回读（M5） | 按标准偏移把中央目录、本地头、CRC、内容全部读回来断言 —— 字节对了但字段位置错，解压软件照样打不开 |
| CRC-32 用标准测试向量 | `"123456789"` → `0xCBF43926`；写错了校验和，解压时会报「文件已损坏」 |
| 1980 年之前的时间戳 | MS-DOS 日期字段是 1980 起算的，不钳制会写出负年份，解压软件拒绝 |
| 队列状态机（M5） | 「某项卡在 converting 永远不动」「导出时把 error 项也算进去」这类问题不会报错，只会静默出错 |
| 逐项参数覆盖的深合并 | `preprocess` 是嵌套对象，浅合并会让覆盖项把其余预处理开关抹成 undefined |
| 改批量参数后旧结果必须作废（M5） | 「参数改了但结果没重跑」会让导出静默混进旧参数跑的图，事后完全无法解释 |
| 写回队列取合成结果 | 手改住在编辑层里，写回时取 `composite(base, edit)` 而不是底图，否则用户在编辑器改了半天、zip 里还是原样 |
| 蓝图图例不许越出画布（M6） | 小图时若只按网格宽度算图例列数，方块名会被画布边缘裁掉 —— 而这正是图纸最有用的部分 |
| 蓝图每格的绘制坐标 | 用替身 canvas 记下 `fillRect` 调用，断言格子落在 `gridX + c*cell`、透明格不画、分页时按偏移取色。这几条错了整张图纸就是废的，肉眼看不出来 |
| 图例色号与 CSV 的 block 一一对应（M6 验收项） | 同一条「色 → 方块」链路从两个出口产出，对不上时照着搭会摆错方块 |
| Y 轴方向 | 图片第一行是上面、MC 里 y 越大越高；照搬格坐标会让人把模型上下搭反 |
| 全不透明网格省略 alpha | 省掉能让文件小一半，但只要有一格不是 255 就必须写 —— 丢了等于丢半透明边缘，程序侧完全看不出来 |
| 名称模板的未知占位符原样保留（M6） | 静默换成空串会产出 `_.png`，用户看不出是自己模板写错了 |
| 导出器默认选项都能直接跑通 | 每个导出器用它自己的默认值实跑一遍，断言产出非空文件。避免「schema 加了选项但 run 里没读」这类空产 |
| 调色板映射表按 hex 键而不是槽位（M6） | 排序 / 合并会改变槽位顺序，按序号存的映射会整体错位且毫无提示 |
| 存档往返：手改必须还在（M7 验收项） | `loadSource` 内部会 `clearResult`，编辑层写在它之前会被清掉，而表现只是「画面少了手改」——不报错、不提示。这条测试直接跑完整的读档路径 |
| 存档摘要字段错一个就整段作废 | 三个数组长度不一致 / 下标越界 / 尺寸非法一律返回 null：读进一半比整段作废更危险，用户不知道少了哪几格 |
| 存档的 source 必须是 data URL | 存成文件路径的话在浏览器里根本拿不回来，属于「写出来能读、读回去没用」的假格式 |
| 大网格网格线降采样 | 两条早退分支：格边长太小不画（否则一片摩尔纹）、可见线数超上限整体放弃。上限按**屏幕上可见**的线数算，不是网格总列数 —— 一张 1000 列的图放大后只有几十条可见线，那种情况该照画 |
| 预设的 preprocess 深拷贝 | 浅拷贝会让「改当前参数」把已存的预设一起改掉，而预设本该是快照 |

测试规模：`npm test` 覆盖 620 个用例。

运行：`npm test`（或 `npm run test:watch`）。

## 12. 关键技术决策记录

| # | 决策 | 结论 | 主要理由 |
| --- | --- | --- | --- |
| 1 | alpha 存储 | 独立 `Uint8Array`，非调色板哨兵值 | 支持半透明；换色不误伤透明区 |
| 2 | 调色板上限 | 256 | 索引存 `Uint8Array`；像素艺术够用 |
| 3 | 手改与转换 | 双层模型（baseGrid + editLayer） | 调参不毁手改，这是全工具最核心的体验承诺 |
| 4 | 手改历史 | 快照式稀疏 Map，非操作日志重放 | 全局换色/自动描边等操作重放语义不清晰 |
| 5 | 转换执行位置 | Web Worker | 主线程不卡；零拷贝传缓冲 |
| 6 | 抖动默认 | `atkinson` | 像素画观感最好、伪影最少，优于 Floyd–Steinberg |
| 7 | 距离默认 | `weighted`（实时）/ `lab`（导出） | 拖动滑块要快，最终出图要准 |
| 8 | UI 框架 | React + Zustand | 面板多；store 能脱离 React 访问，便于画布事件 |
| 9 | 蓝图色→方块 | 按槽位映射到可编辑方块名表，非硬编码 hex 匹配 | MC 无精确同色方块，需人工决策；版本间方块集有差异 |
| 10 | 是否需要后端 | 不要 | 本地隐私、零部署 |
| 11 | 源图传递 | 只在换图时传一次，Worker 常驻持有 | 否则每拖一次滑块就要拷贝一整个源图缓冲（4K 图 = 33MB/帧） |
| 12 | 查找缓存作用域 | **每次转换新建，不跨调用复用** | 缓存内容是按调色板索引的，跨调色板复用会越界。曾因模块级共享缓存导致「切到更小调色板即崩溃」，见下方记录 |
| 13 | 调色板随结果回传 | `ConvertOutcome` 携带本次实际使用的调色板 | 否则快速切换调色板时，先到的旧网格会被新调色板渲染，闪出错误颜色 |
| 14 | 查找缓存不对外暴露 | 由 `createNearestFinder` 内部创建 | 把「传错缓存」这种写法变成不可能，而不是靠注释提醒 |
| 15 | lab 距离缺 LAB 表时报错 | 抛错而非退回欧氏距离 | 静默降级会产出「看起来正常但不对」的结果，比报错难发现得多 |
| 16 | 测试用 node 环境 + 最小 ImageData | 不为一个全局对象引入 jsdom | 顺带把「core/ 不依赖 DOM」这条架构约束变成可被测试强制的规则 |
| 17 | 编辑层的修改方式 | **就地修改 + `editVersion` 版本号**，不每次新建对象 | 拖拽是热路径，每次拷贝编辑层（512×512 = 0.5MB）会让 GC 抖动。代价是渲染方必须订阅版本号，已在 store 注释中写明 |
| 18 | 尺寸变更时的编辑层重采样 | 从**基准层**（`editOrigin`）重采样，不在已重采样的结果上再采 | 拖动「目标格数」滑块会连续触发十几次转换，逐次重采样会把手工编辑一路抹平 |
| 19 | 导出取哪一层 | 导出**合成结果** `composite(base, edit)` | 最容易漏的一处：改了半天的图导出后发现是原样，信任一次就没了 |
| 20 | 吸管的实现位置 | 不进 `core/tools/` 的回调体系，由笔画控制器直接读写 store | 它不改网格，只改前景色；为它给工具接口开一条「写回值」的通道得不偿失 |
| 21 | 椭圆的画法 | 包围盒掩码 + 取边界，不用中点椭圆算法 | 3×3～8×8（像素画常用区间）下中点算法给出的线断开且不对称 |
| 22 | 棋盘格底的画法 | CanvasPattern，不逐格 `fillRect` | 铺满一屏要上万次 fillRect，而鼠标每动一下都要重绘 |
| 23 | 分割视图的落笔范围 | 只在分割线**右侧**可画 | 左侧是原图，在那里落笔画的是看不见的地方；直接禁掉整个视图又太严 |
| 24 | 撤销记录存 before / after 两侧 | 两侧都存，不做「一份快照 + 方向约定」 | 重做需要知道改成什么；省下的那点内存换不来语义清晰 |
| 25 | 全局换色改哪一层 | **写进编辑层**，不改底图 | 底图由参数重算得出，改它下次调参就白改；编辑层天然持久、天然可撤销 |
| 26 | 改色 / 排序 / 合并不入撤销栈 | 不入栈，但**必须同步重映射底图与编辑层的索引** | 它们动的是调色板本身（与转换参数同理）；漏掉编辑层的重映射会静默改变手改像素的颜色 |
| 27 | 内置调色板可否就地修改 | **只读，改色先分叉出自定义板** | 就地改共享常量会让所有用同一块板的地方一起变色，刷新后又恢复 |
| 28 | k-means 在哪张图上聚类 | 降采样后的图（≤256×256 格） | 原图 400 万像素要几百毫秒；目标的颜色分布用像素图自身就已经足够代表 |
| 29 | k-means 的初始化 | 最大最小距离法（farthest-first），不用随机采样 | 结果必须确定：每拖一次滑块调色板都变的话，手改的颜色会跟着乱跳 |
| 30 | 提色结果是否自动套用 | 不自动，先预览再让用户决定存不存 | 提色很像抽奖，直接覆盖当前调色板会很恼人 |
| 31 | 合并近似色的算法 | 贪心（保留先出现的槽位），不用聚类 | 槽位顺序本身有意义（用户按顺序认色），聚类会打乱顺序且「保留哪一个」不可预测 |
| 32 | 合并容差的滑块 | 不用控件库的 `Slider`，用裸 `input[type=range]` | 库里的 Slider 会置位 `interacting` → 拖容差时触发一轮无谓的「快速模式」重算 |
| 33 | 明暗分层的映射方式 | 档位只定「目标亮度」，候选色取整块调色板的最近色 | 同档内取最近会退化成空操作（最近的是自己）或乱换色相（同亮度的别的色）；「三层压成三个固定色」又会把红苹果和绿苹果压成同一个色 |
| 34 | 自动辅助的写入路径 | 返回 `CellWrite[]` 由 store 统一落库 | 与画笔共用一套记账 → 每个辅助操作天然可撤销、不被重算冲掉 |
| 35 | 色晕清理的触发位置 | 放进 `preprocess`，且在 α 阈值**之后** | 它要靠「谁还是半透明」判断边缘；放前面会连背景色一起搬 |
| 36 | 色晕清理跳过超大图 | 超过 1600 万像素直接不做 | 需要一张与像素数等长的标记数组（16MB）；不值得为边缘三圈像素付这份内存 |
| 37 | 平铺预览的几何量取整 | 开启预览时把 pan/zoom 取整 | 非整数缩放会让相邻两份之间出现 1px 接缝 —— 那正是预览想暴露的问题，不能由渲染自己制造 |
| 38 | 批量参数是否与编辑器共用 | **各一份**，另给一个「从当前参数同步」按钮 | 共用看起来省事，但批量在后台出素材时你随时在调编辑器的参数，两边会互相串改：既不知道批量用的是哪套，刚调好的预览也被改了 |
| 39 | 批量转换的 Worker | 新开一个 `PipelineRunner` 实例 | 单图那个 Runner 只持有一张源图，且会把待处理请求合并成最新一条（为拖滑块设计的）；批量挤进去会顶掉编辑器正在看的图 |
| 40 | 批量解码用哪条路径 | `decodeImage()`，不生成显示位图 | `loadSourceImage()` 会额外留一份最长边 2048 的预览位图（每张好几 MB），队列里根本用不上 |
| 41 | 逐项参数怎么存 | 只存 `override` 差异，运行时与批量参数合并 | 存全量的话，改一次全局参数就得逐个项去改；存差异只有一处合并逻辑 |
| 42 | 逐项覆盖的合并 | `preprocess` 深合并 | 嵌套对象浅合并会让覆盖项把其余预处理开关抹成 `undefined` |
| 43 | 批量改名了参数怎么办 | 该退回归「待处理」并丢弃旧结果，同时比对「本轮参数指纹」提示结果已过期 | 静默导出旧参数的结果，是这功能里最难发现的一类错 |
| 44 | ZIP 打包 | 自己写 store 模式写入器，不引 `fflate` | 输入全是 PNG（内部已是 DEFLATE），二次压缩收益不到 1%，不值得为它加依赖；见 §7.1 |
| 45 | 命名去重的比较方式 | 忽略大小写 | Windows / macOS 默认不区分大小写，`A.png` 与 `a.png` 会互相覆盖 |
| 46 | 未知占位符的处理 | 原样保留在文件名里 | 静默换成空串会产出 `_.png`，用户看不出是自己模板写错了 |
| 47 | 队列长列表 | 不做虚拟滚动 | 队列是用户自己拖进来的，几十项以内；虚拟滚动会让「展开某项改参数」变复杂 |
| 48 | 手改结果怎么进 zip | 编辑器里那个队列项上给一个显式的「写回队列」按钮，取 `composite(base, edit)` | 手改住在编辑层，队列项只有一份参数产物的网格；不写回就会「改了半天导出还是原样」，属于静默丢改动 |
| 49 | 导出参数怎么定义 | 导出器自带选项 schema，面板照 schema 渲染 | 加导出器不用改面板；范围/默认值/提示只有一处定义，不会两边对不上 |
| 50 | 选项值的合并方式 | 按 schema 的 key 逐个取，不展开合并 | 展开合并会让已删掉的旧选项一路留在状态里再被写回存储，越积越多 |
| 51 | 精灵图集的输入 | 取批量队列的已完成项 | 图集本就是多图产物，单文档编辑器里一次只有一张图，做成单图图集没意义 |
| 52 | 图集槽位尺寸 | 所有槽位等大（取最大图的尺寸），图在槽内居中 | 引擎按固定帧尺寸取图；各格大小不一会让取帧逻辑变复杂 |
| 53 | 方块映射的键 | 颜色的 hex，不是调色板槽位序号 | 排序/合并会改变槽位顺序，按序号存的映射会整体错位且毫无提示 |
| 54 | 方块映射的默认值 | 按加权 RGB 找「离该颜色最近的方块」，不硬编码 | MC 没有精确等于某个 hex 的方块，匹配天然是「最接近」；硬编码只能覆盖内置板 |
| 55 | 蓝图的文字 | 用 canvas `fillText`，不自绘点阵字体 | 图例要写中文方块名，点阵字体覆盖不了；代价是这一支不能纯函数单测，所以布局与 CSV 拆成纯函数，绘制坐标用替身 canvas 测 |
| 56 | 蓝图 Y 轴默认方向 | 图上第一行 → y 最大 | 图片第一行是上面，MC 里 y 越大越高；照搬格坐标会让人把模型上下搭反 |
| 57 | 多文件导出 | 默认打包成 zip，复用 M5 的 ZIP 写入器 | 分页蓝图一导就是好几张，连续下载会被浏览器当可疑行为拦下 |
| 58 | 图例区的宽度 | 参与画布宽度计算（可能反过来撑宽画布） | 小图时只按网格宽度算列数，方块名会被画布边缘裁掉 —— 那正是图纸最有用的部分 |
| 59 | 存档要不要内嵌源图 | 内嵌（导入时的原始字节） | 浏览器记不住本地文件路径，存引用等于每次打开都要重选一次原图 |
| 60 | 存原始字节还是重编码 PNG | 原始字节 | JPEG 原样存比「解码后再编码成 PNG」小 3–5 倍；反正解码在浏览器里很快 |
| 61 | 编辑层在存档里的形式 | 三数组 CSR 稀疏 | 直接 JSON 存 `(PixelCell\|null)[]` 要 26 万个 null 字面量，稀疏能小三个数量级 |
| 62 | 读档时重算还是用存档的网格 | 用存档的 `baseGrid`，不重算 | 重算是异步的，编辑层会在结果到达前被判为「尺寸不符」而重建 → 手改静默丢失 |
| 63 | 读档的写入顺序 | 先 `loadSource`（内部 clearResult），后写编辑层 | 顺序反了编辑层会被 clearResult 一起清掉，而表现只是「画面少了手改」 |
| 64 | 存档校验的粒度 | 分三段独立校验，坏哪段丢哪段 | 编辑层坏了不该让整份存档打不开；但也绝不「读进一半」——那会让用户不知道少了哪几格 |
| 65 | 要不要自动把当前工作存进 localStorage | 不要 | 刷新后悄悄回来一张图，会让人以为没关掉；显式存档 + 长期偏好自动存，分工清楚 |
| 66 | 离线构建的字体 | 去掉 Google Fonts 外链 | 离线版留一行外链请求等于自己拆台；CSS 里本来就写了系统字体 fallback |
| 67 | 离线构建的形式 | JS/CSS 全部内联进单个 index.html | 浏览器拦的是「从 file:// fetch 外部 module 脚本」，内联脚本不受限 |
| 68 | 离线版放弃 Worker | 接受（状态栏明确显示「已降级 主线程」） | file:// 下拉不到独立 worker 文件。功能全在，只是拖参数略卡；把这个代价写进 README 而不是藏起来 |

### 关于决策 12 的踩坑记录

最初把 5bit 查找缓存做成模块级单例，想省掉每次转换 64KB 的分配。结果切换调色板
（16 色 → 8 色 / 2 色）时崩溃，因为缓存里存的索引来自旧调色板，越界取到 `undefined`。

**教训**：省下的那点分配（64KB 清零，微秒级）远小于它引入的风险。
缓存这类「按某个上下文建立」的结构，作用域必须小于或等于它依赖的上下文的生命周期。
现在 `QuantizeOptions.cache` 的注释里写明了这个约束。
