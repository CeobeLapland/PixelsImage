- [x] `palettes/builtin.ts`：Minecraft 16 染料色 + 灰阶 8 级 + 黑白 2 色
- [x] `core/pipeline.ts`：串起完整流水线，纯函数 `convert(imageData, settings) → PixelGrid`
- [x] `core/workers/pipeline.worker.ts` + 主线程调用封装（transferable 传递、请求合并）
- [x] `ConvertPanel.tsx`：目标格数、采样方式、调色板、距离度量、抖动算法、抖动强度、预处理

- [x] `core/preprocess.ts`：亮度/对比度/饱和度/锐化/alpha 阈值（原本排在 M4，因为参数必须在下采样前生效，提前到 M1）
- [x] 对比视图：侧滑分割 / 并排 / 仅结果 / 仅原图（原计划只做前两种）

**验收**：
- 拖入照片 → 设 32×32 + Minecraft 调色板 + Atkinson → 得到正确的方块感像素图；
- 拖动尺寸/抖动滑块预览流畅（不出现明显掉帧）；
- 导出的 1x PNG 在 Photoshop 里放大后是干净硬边，无插值模糊。

**已知修复**（浏览器实测发现）：
- 切换调色板到更小的板（16 → 8 → 2 色）时崩溃。根因是模块级共享的 5bit 查找缓存
  未随调色板失效，旧索引越界。已改为每次转换新建缓存，见 DESIGN.md 决策 12。
- `dominant` 采样的直方图 `touched` 列表容量不足（4096），大格子里颜色超过这个数时
  会漏投票并偏向先扫到的颜色。已改为与直方图等长。

- 开四向对称画角色脸部，落笔即四向同步 → `tools/index.test.ts` 覆盖镜像与去重

**实现时的取舍**（都记进了 DESIGN §12 决策 17–20）：
- **编辑层就地修改 + 版本号**，而不是每次拷贝新对象。拖拽是热路径，
  拷贝 512×512 的编辑层每帧就是 0.5MB 的垃圾。代价是渲染方必须订阅
  `editVersion` 才能感知变化 —— 这一点在 store 的注释里写明了。
- **尺寸变更从「基准层」重采样**。若在已经重采样过的结果上再采一次，
  拖动「目标格数」滑块连续触发的十几次转换会把手工编辑逐次抹平。
- **导出走 `composite`**：这是最容易漏的一处 —— 改了半天导出的还是原图。
- **吸管不做成工具函数**，而是笔画控制器直接读 store 写前景色：
  给它一个「写回值」的通道会让工具接口变复杂，而它本来就不改网格。

**待浏览器真机确认**（用户自行测试）：
- 拖拽绘制、图形预览、选区搬运的手感与光标反馈
- 大网格（128×128 以上）下的重绘流畅度

- [x] 自定义调色板的持久化（localStorage）
- [x] 色槽颜色编辑（原生取色器；改内置板自动分叉出自定义板）

**验收**：
- 从一张插画提出 12 色自定义调色板 → 套用到另一张图 → 把其中一色全局替换 →
  手改区域的颜色也被同步替换，且可一键撤销 → `state/palette.test.ts` 覆盖了换色 + 撤销 +
  编辑层同步；提色与套用需要真机走一遍
- `extract.test.ts` 锁住「四个纯色块能被还原成四个色」「透明区不参与提色」
- `ops.test.ts` 锁住最危险的一条：排序/合并后**画面必须不变**（索引与调色板同步重映射）

**实现时的取舍**（记进 DESIGN §12 决策 25–29）：
- **全局换色写进编辑层，不改底图**。底图是「由参数重算得出」的，改它会在下次调参时白改；
  写进编辑层则天然持久、天然可撤销，代价是「手改格数」会跳一截（那些格子确实被改过了）。
- **改色 / 排序 / 合并不进撤销栈**（与转换参数同理：它们动的是调色板本身，不是画布内容），
  但**必须同步重映射底图与编辑层的索引** —— 漏掉编辑层的话画面看着正常，
  用户手改的格子却会突然变色，属于最难排查的一类 bug。
- **内置板只读**：任何改色操作先分叉出一块自定义板。直接改共享的内置对象会让
  所有用同一块板的地方一起变色，而且刷新后又恢复。
- **k-means 从降采样结果上聚类**，不在原图上跑：原图 400 万像素要几百毫秒，
  而目标格数最多 6.5 万格，其颜色分布已经足够代表最终这张像素图。
- **提色结果不自动套用**，先给预览再让用户决定存不存 —— 提色很像抽奖，
  直接覆盖当前调色板会很恼人。

**同类工具常见的坑，这里刻意避开的**：
- 提色结果里混进一堆背景色 → 提供「排除透明像素」与「限定明度区间」两个过滤器
- 拖动合并容差时触发转换重算 → 这一处没用控件库的 `Slider`（它会置位 `interacting`）

**待浏览器真机确认**：
- 提色在真实照片/插画上的取色质量（中位切分 vs k-means 哪个更合手）
- `<input type="color">` 在系统取色器里的表现
- 导入各来源的 `.hex` / `.gpl` 文件是否都能识别

      （core 在 M1 就写好了，但一直没有 UI，等于用不了）
- [x] 去背后的边缘色晕清理（`preprocess.applyDecontaminate`）
- [x] Onion skin —— M2 已提前落地（「编辑」分组的「原图叠加对照」）
- [x] 3×3 平铺预览 + 接缝检查（对不上的边界格在画布上标红）
- [x] `AssistsPanel.tsx` + `PreprocessPanel.tsx` 控件面板

**验收**：一张带白底的角色图 → 一键去背 + 自动描边 + 自动明暗 → 直接是可用的素材，
无需手改超过 5 笔 → 真机验收

**实现时的取舍**：
- **明暗分层不改变色相**：把颜色**缩放到目标亮度**（压暗按比例乘、提亮朝白 lerp），
  再在整块调色板里找最接近的色。这里走过一次弯路 —— 若按格自身亮度归类后只在**同档**里
  找最近色：包含原色则最近的永远是它自己（模块空操作），排除原色则等于换成同亮度、
  别的色相的兄弟色（中灰变中红），比空操作更糟。
- **去背是两个开关配合**：α 阈值判「哪些像素算背景」，色晕清理负责把边缘那圈残留的背景色擦掉。
  只用阈值会留下一圈灰边 —— 这一点在面板上直接写出来提醒。
  色晕清理只改 RGB 不动 alpha，所以边缘的柔和过渡该保留还保留，只是它通往的颜色换成了主体色。
- **超大图跳过色晕清理**：它需要一张与像素数等长的标记数组（1600 万像素 = 16MB），
  再大就不值得为边缘那三圈像素付这份内存。
- **平铺预览把几何量取整**：非整数缩放下相邻两份之间会出现 1px 接缝，
  而那正是这个预览想让你看见的东西，不能由渲染自己制造出来。
- **辅助操作全部写进编辑层**：因此每一个都能 Ctrl+Z 撤销，也不会被转换参数重算冲掉。

**待浏览器真机确认**：
- 描边在真实素材上的观感（4/8 邻域、外缘/内缘哪个更常用）
- 明暗分层在两个阈值取不同值时的效果是否够「可用」
- 去背在真实白底/绿幕素材上的效果，特别是色晕清理的圈数（3 圈）够不够

**验收**：拖入 20 张参考图 → 用同一套参数转换 → 一次导出 zip，里面 20 张命名正确的像素图 → 待真机验收

**实现时的取舍**（记进 DESIGN §12 决策 38–47）：
- **批量参数是独立的一份**，不与编辑器共用，靠一个「从当前参数同步」按钮对接。
  共用看起来省事，但批量在后台出素材时你随时在调编辑器的参数，两边会互相串改。
- **另开一个 Worker 实例**跑批量。单图那个 `PipelineRunner` 只持有一张源图，
  且会把待处理请求合并成最新一条（那是为拖滑块设计的）；批量挤进去会顶掉编辑器正在看的图。
- **批量解码走 `decodeImage()`**，不生成显示位图 —— 20 张图各留一份 2048px 预览就是几百 MB。
- **zip 自己写，不引 `fflate`**。输入全是 PNG，而 PNG 内部已经是 DEFLATE 压缩数据，
  二次压缩收益不到 1%，不值得为它加依赖。store 模式的 ZIP 一百多行能写对，
  而且能被单测按标准偏移回读校验（顺带用系统解压器实测过一遍）。
- **命名去重忽略大小写**：Windows / macOS 默认不区分大小写，`A.png` 与 `a.png`
  在 zip 里是两个条目，解压时却会互相覆盖。
- **参数改了就丢弃旧结果**：改批量参数会让该项退回「待处理」并清掉上次的结果，
  否则导出时会静默混进旧参数跑的图 —— 这是这功能里最难发现的一类错。
- **手改要显式「写回队列」**：队列项手里只有一份参数产物的网格，手改住在编辑层里。
  跳去编辑器微调后，点该项上的「写回队列」把合成结果（含手改）覆盖回队列，zip 才会带上。

**真机待确认**：
- 20 张真实参考图跑一轮的总耗时与内存占用（队列里每项都留着一份结果网格）
- 队列缩略图的观感（画的是转换结果的那张小图，不是原图）
- 系统解压器对导出 zip 的兼容性（已在 Windows 上验证过一遍）

**实现时的取舍**（记进 DESIGN §12 决策 49–56）：
- **导出器自带选项 schema**，面板照 schema 渲染控件。加一个导出器只写一个对象，
  不用再动面板；选项的范围与提示只有一处定义，不会出现「面板限 1–64、导出器按 1–32 处理」。
- **蓝图是施工图，不是效果图**：要的是能照着搭，所以有行列标尺、每页自洽的色号图例、
  以及图例区会反过来撑宽画布（小图时若只按网格宽度算列数，方块名会被画布边缘裁掉 ——
  而那正是图纸最有用的部分）。
- **方块映射按颜色 hex 键，不按槽位序号**：槽位顺序会被排序 / 合并近似色改变，
  按颜色键才不会错位。默认值用「离该颜色最近的方块」算出来 ——
  MC 没有精确等于某个 hex 的方块，颜色匹配本来就得人工决策；硬编码只能覆盖内置板。
- **Y 轴默认「图上第一行在最高处」**：图片第一行是上面，而 MC 里 y 越大越高，
  直接照搬格坐标会让人把模型上下搭反。
- **多文件默认打包成 zip**：分页蓝图一导就是好几张图，连续下载会被浏览器当成可疑行为拦下；
  这里直接复用 M5 那个 ZIP 写入器，没多写一行打包逻辑。
- **架构分层**：布局与 CSV 是纯函数（可单测），只有 PNG 需要 canvas 的 `fillText`
  —— 图例里要写中文方块名，自绘点阵字体覆盖不了。所以 `renderBlueprintPage`
  用替身 canvas 测绘制坐标，而不是整支跳过。

**真机待确认**：
- 32×32 与 64×64 的图纸在 A4 打印下的可读性（每格像素取多少合适）
- 系统剪贴板能否粘进你常用的聊天窗 / 编辑器（剪贴板 API 需要 https 或 localhost）
- 列标尺的疏密（每 4 格标一次在小图上会不会太挤）

`npm run build:offline` 后把 `dist-offline/index.html` 拷到另一台电脑双击可用 → 待真机验收。

**实现时的取舍**：
- **源图内嵌进存档**，不存引用。浏览器记不住本地文件路径（File 不允许序列化路径，
  File System Access API 又要重新授权），存引用等于第二天打开存档时让你「重新选一次原图」，
  那这个存档基本没用。代价是文件大，所以存的是**导入时的原始字节**（JPEG 原样存），
  而不是「把解码后的像素重新编码成 PNG」—— 后者对照片要大 3–5 倍。
- **编辑层稀疏存**（三数组 CSR）。512×512 的编辑层直接 JSON 存要 26 万个 `null` 字面量；
  手改通常几百格，稀疏存能小三个数量级。
- **读档时先清空再写入**。`loadSource` 内部会 `clearResult`（换图必须作废旧结果），
  编辑层写在它之前就会被一起清掉 —— 而且画面上「只是少了手改」，不报错不提示。
  这条已由测试锁死。
- **读档不重算**，直接用存档里的 `baseGrid`。重算是异步的，编辑层会在结果到达前
  被判为「尺寸不符」而重建，手改同样会丢。存档里本来就带了网格，没必要再算一遍。
- **快照文件（`.pixproj`）与自动持久化（localStorage）分工不同**：存档是给「一份工作」
  用的，显式存、显式取；调色板 / 预设 / 方块映射是「长期偏好」，自动存。
  刷新页面不该丢偏好，但也不该悄悄把当前这张图留下 —— 那会让人以为「我明明关掉了」。
- **离线构建删掉 Google Fonts 的那三行 link**。日常构建留着，图的是设计味道；
  但离线构建的意义就是不联网，留一行外链请求等于自己拆台（离线时自动退回
  CSS 里写好的系统字体栈）。顺带把 sourcemap 关掉：内联之后 .map 指向的文件已不存在。
- **离线版是单线程的**：file:// 下拉不到独立的 worker 文件，会走主线程降级路径，
  状态栏显示「已降级 主线程」。功能全都在，只是拖参数略卡 —— 这个取舍写进了 README。

**真机待确认**：
- 存档在真实尺寸素材上的文件大小与读写耗时（内嵌源图的代价）
- 离线单文件在 Chrome / Edge 下双击是否真的能跑（预期：能跑，但状态栏显示「已降级 主线程」）
- `?` 键在不同输入法状态下的可触发情况（也认 `/` 作为备用）

## M8 · 动图（序列帧）

**目标**：把「动图 → 像素化 → 动图」这条线走通，且不为此新建一套动画数据模型。

- [x] 动图拆帧：GIF / WebP 拖进批量队列 → 自动拆成逐帧 PNG（`名字_001.png`…），原始帧时长随帧走
- [x] 按**文件头**识别格式（64KB 嗅探）：伪装成 `.jpg` / `.png` 的动图也能拆
- [x] 单图入口分流：拖到画布时先 `probeAnimation` 读帧数，真动图转去批量队列、静态 GIF 照常进编辑器
- [x] `core/gif/encode.ts`：自写 GIF89a 编码器（GCT/LCT、LZW、1 位透明、循环扩展、整数倍放大）
- [x] 导出器 `gif`：帧序取自批量队列，可设帧延时 / 循环次数 / 放大倍数
- [x] `buildAseFrames` + 导出器 `aseAnim`：多帧 `.ase`，每帧时长写进帧头
- [x] 帧尺寸一致性校验：不一致时报错，并点名「裁透明边」这个最常见原因
- [x] 面板提示：GIF 的 1 位透明与 256 色上限、拆帧需要 Chrome / Edge、队列顺序即帧序

**验收**：一张 GIF → 拖进队列（拆成 N 帧）→ 转换 → 导出 GIF，帧序与节奏不变；
导出 `.ase` 后在 Aseprite 里是 N 帧、每帧时长正确 → 结构与时长已用第三方解析器核对，真机待验收

**实现时的取舍**：
- **队列即帧序列**，不新建动画模型（详见 DESIGN §7.3）。队列已有的逐项参数、命名模板、
  并排对比、送进编辑器手改，全都直接复用。
- **帧落成 PNG 文件**再入队：编辑器打开、重新解码、打包 zip 三条路径一行都不用改。
- **格式看文件头**而不是扩展名：动图被另存成 `.jpg` 是常事，看名字会静默只取第一帧。
- **单图入口先 probe 再分流**：`probeAnimation` 只读 `frameCount`、不解码像素，
  所以「拖到画布」不会为了判断动图而变慢；静态 GIF 不会被误送去队列。
- **拆帧不支持时直接报错**：静默只取第一帧会让人以为动图「就是这样」。
- **不引 `gifenc`**：输入已经是调色板索引 + alpha 的网格，编码只剩查表 → LZW → 拼块；
  LZW 的码宽增长时机是最容易写错的点，用「独立解码器 + 真实 .NET/GDI+ 解码」两路验证。
- **`.ase` 不写 frame tag**：布局在 spec 里几经变动，写错整份文件打不开；没有标签照样能播放。
- **图层块只写在第一帧**：图层是文档级定义，每帧重复会让 Aseprite 里出现 N 个同名图层。

**真机待确认**：
- Chrome / Edge 下拖入 GIF 的拆帧速度与内存（大尺寸 + 多帧）
- 伪装成 `.jpg` 的动图在批量队列与画布两个入口都能被识别
- 把动图拖到画布确实转去队列并给出一句提示（而不是替换当前编辑的图）
- Firefox 下拖入 GIF 是否给出那句明确提示（而不是静默单帧）
- 导出的 GIF 在聊天窗 / 浏览器 / 系统看图器里能否正常播放、透明是否正确
- `.ase` 在 Aseprite 里打开是否为 N 帧、时长与颜色是否正确（结构已核对，观感待看一眼）
